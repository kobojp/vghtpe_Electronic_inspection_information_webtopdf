固定發布 GitHub Release 操作手冊

適用於「水電消防報表下載系統」。程式碼合併到 main 後，只要推送新的版本標籤，GitHub Actions 就會自動測試、編譯，並發布包含 EXE 與 data.json 的 ZIP。

每次發布只要完成這 5 步

  1. 完成修改與測試
  2. 提交 PR
  3. 合併至 main
  4. 推送新版本標籤
  5. 確認 Release
自動流程正常時，不需要在 GitHub 網站手動建立 Release，也不需要自己壓縮或上傳檔案。

第一次使用前確認

  • .github/workflows/release.yml 已經合併到 main。
  • GitHub Actions 頁面可看到 Build and Release 工作流程。
  • 本機 Git 已設定好 GitHub 權限，且可執行 git fetch 與 git push。

以上設定只需確認一次。之後每次改版直接依照下一節操作。

固定發布流程

  1. 修改完成後執行測試

    pipenv sync
pipenv run python -m unittest discover -s tests -v

    確認所有測試顯示 OK，再提交程式碼。

  2. 將修改提交到功能分支

    git status
git add README.md main.py tests
git commit -m "說明本次修改內容"
git push

    請依實際修改檔案調整 git add，不要把下載的 PDF、測試輸出或不相關檔案一起提交。

  3. 在 GitHub 建立 PR，確認後合併到 main

    PR 合併完成後再建立版本標籤。標籤若指向合併前的提交，Release 就不會包含最新修改。

  4. 設定新版本號並推送標籤

    git fetch origin main
$version = "v5.0.1"
git tag $version origin/main
git push origin $version
    每次都要換成尚未使用過的新版本號。例如下一版使用 v5.0.2，不可重複推送 v5.0.1。

  5. 確認 Actions 與 Release

    到 Actions 查看 Build and Release。綠色勾勾代表測試、編譯與發布都已完成，再到 Releases 確認 ZIP 已附加在該版本下方。ZIP 內應同時包含 EXE 與 data.json。

    開啟 GitHub Actions 開啟 Releases

版本號怎麼決定

改版類型 範例 使用時機
修正版 v5.0.1 → v5.0.2 修正錯誤、微調介面或文件。
功能版 v5.0.2 → v5.1.0 新增功能，原本使用方式仍可繼續使用。
大改版 v5.1.0 → v6.0.0 使用方式或檔案格式有重大變更。

常見問題

推送標籤後沒有執行 Actions

確認標籤以小寫 v 開頭，例如 v5.0.1，並確認 Release workflow 已存在於該標籤指向的提交。

顯示標籤已存在

代表版本號已經用過。不要覆蓋舊標籤，改用下一個新版本號，例如 v5.0.2。

Actions 顯示紅色叉叉

點進失敗的步驟查看錯誤。若是測試失敗，先修正程式並重新合併，再建立另一個新標籤；不要重複使用失敗版本的標籤。

Release 內沒有 ZIP，或 ZIP 缺少檔案

先確認 Actions 的「Build Windows executable」、「Package release archive」與「Create GitHub Release」皆成功。ZIP 內應包含 水電消防報表下載系統.exe 與 data.json。
